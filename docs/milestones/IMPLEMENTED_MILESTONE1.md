# Milestone 1 — Runtime Engine · Implemented

> Current step (M1) — turns the org charts generated by M3 into *live agents*.

## 1. What this milestone delivers

A provider-agnostic runtime that loads an `Org`, runs a designated role on a
task through a real agent loop, and records the outcome in durable SQLite
state. It was built to the plan agreed with the user:

- **Provider strategy:** a single `LLMClient` interface; **OpenAI is the default**
  real provider; **Ollama** covers local models (Gemma/Qwen); **Fake** is the
  offline test path. Stubs used wherever a third-party tool isn't wired.

- `jobs` — `--org [--status --limit]`

## 3. Agent loop (JSON action protocol)

The model responds to a system prompt (charter + SOP + goals + granted tools +
approval rules) in a small JSON protocol:

```
{"type":"final","output":"<answer>"}
{"type":"tool","tool":"<tool_name>","tool_input":{...}}
```

Loop, up to `max_steps`:
1. `llm.complete(...)`, then `parse_action()` (handles JSON + fenced JSON + plain-text fallback).
2. `final` → record result, mark job `done`.
3. `tool` → check the call is in the role's **granted tools**; if `requires_approval`
   and not approved → log `approval` denial, tell the agent to stop, continue.
4. Execute the tool, append its result to the chat, continue.

Provider-agnostic **by construction** — every provider just returns text.

## 4. Tools & permissions

- Real built-ins: `files_read`, `files_write` (approval-gated), `web_fetch`.
- Stubs for the rest (`notion`, `gmail`, …, `analytics`) return an explicit
  "STUB: not wired in M1" message, so grants and the loop are real even when
  the adapter isn't.
- `tools_for_role(role)` resolves `tool_grants` → only granted tools are exposed;
  a schema-level `requires_approval` overrides the tool default.

## 5. SQLite state

`Store` with `jobs`, `results`, `events`. Supports enqueue, pull-next (claims
running), complete, fail, block, filtering, and event logging. Interface is
narrow so it can be swapped for Postgres in M5.

## 6. Providers

- **OpenAI** (default): set `OPENAI_API_KEY`. The adapter uses the modern
  `openai>=1.0` client.
  Optional `OPENAI_BASE_URL` for compatible endpoints.
- **Ollama**: `http://localhost:11434/v1` (or `OLLAMA_BASE_URL`), defaults to
  model `gemma4` (or `OLLAMA_MODEL`) — pass `--model`/provider config as needed
  for Gemma/Qwen.
- **Fake**: no network; used by tests and `--provider fake`.
- Selection: `AGENT_FACTORY_PROVIDER` env or `--provider` flag.

## 7. CLI usage

```
set PYTHONPATH=src
set AGENT_FACTORY_PROVIDER=openai        # optional; openai is default
set OPENAI_API_KEY=...

# OpenAI
python -m agent_factory run --org orgs/Acme --role worker_research_1 ^
    --task "Summarize the quarterly targets." --approval ask

# Local Ollama (Gemma/Qwen)
python -m agent_factory run --org orgs/Acme --role worker_research_1 ^
    --task "Summarize the quarterly targets." --provider ollama --approval ask

# Explicit model override
python -m agent_factory run --org orgs/Acme --role worker_research_1 ^
  --task "Summarize the quarterly targets." --provider ollama ^
  --model qwen2.5:7b --approval ask

# Offline smoke test (no API key)
python -m agent_factory run --org orgs/Acme --role worker_research_1 ^
    --task "List the targets." --provider fake --approval deny

python -m agent_factory jobs --org orgs/Acme
```

`--approval` is `ask` (interactive prompt), `allow` (auto), or `deny` (auto-deny).

## 8. Test coverage

Added `tests/test_runtime_state.py`, `test_runtime_tools.py`,
`test_runtime_agent.py`. At the time of M1 the combined suite stood at **87 tests, all offline / green**

```
python -m unittest discover -s tests
```

Notable behaviors verified:
- Store enqueue → pull (running) → complete; fail/block; filtering; events.
- Tools: read grant exposes only read; write grant gated; unknown tool → stub.
- Agent loop: direct final; tool-then-final; approval denied blocks execution;
  approval allowed writes file; unknown tool recovers; max-steps raises
  `AgentLimitError`.
