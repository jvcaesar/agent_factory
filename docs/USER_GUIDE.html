🤖 Agent Factory — User Guide

A practical, step-by-step guide to the agent_factory CLI. The offline examples use the deterministic fake provider, so you can reproduce every command without an API key. Real model output requires OpenAI or a local Ollama server.

✅ All examples verified 🔌 Works offline (fake provider) 🐍 Python 3.10+ 🧪 146 tests green
🧭
How to read this guide. Each command section follows the same pattern: Purpose → Command → Expected output → Notes. Sections are ordered the way you would actually use the tool: create a workforce → run work → make it proactive → observe it → talk to it.

🧠 The mental model in one paragraph

You bootstrap an org chart (roles, SOPs, goals) from a short interview, a YAML spec, or a pre-built pack. Each role becomes a runnable agent backed by an LLM. Work runs through a durable SQLite store in the org folder (jobs, context, insights, messages), so every job, proposal, finding, and channel conversation is recorded and queryable. Guardrails (risk tier + approval policy) are enforced on every tool call, and the human talks to agents through a shared channel.

1Installation and setup

📋
Purpose: get the CLI installed and pick an LLM provider.
install from the repo root
py --version                     # requires Python 3.10+
py -m pip install -e .           # core: pydantic and pyyaml
py -m pip install -e ".[openai]" # OpenAI support, when needed
# or: py -m pip install -e ".[ollama]"  # local Ollama support

Select a provider in the current PowerShell session. fake is the best first run:

PowerShell — pick ONE provider
$env:AGENT_FACTORY_PROVIDER = "fake"       # offline, deterministic
# $env:AGENT_FACTORY_PROVIDER = "openai"   # also set OPENAI_API_KEY
# $env:AGENT_FACTORY_PROVIDER = "ollama"   # Ollama at localhost:11434

The environment variable lasts for the current terminal session. The CLI also accepts --provider for a single command.

Check that your providers are reachable — probe

terminal
agent_factory probe
✔ expected output (working provider)
Probing 3 configured provider/model pair(s)...

[OK]   openai  gpt-4o-mini           0.9s  -> 'OK'
[OK]   openai  gpt-4o                1.4s  -> 'OK'
[OK]   openai  o1                    2.1s  -> 'OK' [reasoning-fallback]

3/3 reachable.

probe pings every MODEL_* pair configured in your environment (or the provider's built-in defaults if none are set) and reports one [OK] / [FAIL] line per pair. Exit code is 0 only if all pairs answer. Limit it with --only openai or --only ollama.

🧪
Running the tests? They are fully offline: py -m unittest discover -s tests (146 tests, no API keys).

3Create your workforce

📋
Purpose: turn intent (an interview, a spec file, or a pack) into a validated org chart on disk: org.yaml, settings.yaml, per-role YAML + SOPs, and goals/current.md.

3.1  bootstrap — three ways to generate an org

Recommended first

📦 A — Pre-built pack

Pick a ready-made workforce (business_ops, engineering, research) and just name it.

Conversational

💬 B — Interactive interview

Answer questions about goals, domains, tools, and risk; the chart is generated and validated.

Repeatable

📄 C — YAML spec

Non-interactive generation from a checked-in spec file — ideal for CI or templates.

option A · list packs, then bootstrap
agent_factory packs                                   # see what is available
agent_factory bootstrap --pack business_ops --name "Demo Co" ^
    --north-star "Become the trusted advisor for our clients" --out orgs/Demo
✔ expected output of  packs
business_ops    Business Operations         Go-to-market and operations workforce: marketing, operations, support, finance, data, and partnerships.
engineering     Software Engineering        Delivery-focused workforce: product, engineering, research, data, and agent-operations.
research        Research & Analysis         Evidence workforce: research, data, product-use, and partnership research.
✔ expected output of  bootstrap --pack
Generated org 'Demo Co' at: orgs/Demo
  pack: business_ops
  roles: 23  lead=True  risk=review_external  budget=medium
  top -> lead_exec (Org Lead (Chief of Staff), proactivity 5)

Each pack ships a ready-made spec you can use directly, e.g. agent_factory bootstrap --spec examples/packs/research.yaml --out orgs/Research.

option B · interactive interview
agent_factory bootstrap

You will be asked for: the workforce name, your (founder) name, the north-star goal, 2–3 quarterly targets, which domains to staff, which tools roles may use, and the risk/budget tiers. Answers are written to orgs/<name>/ when the generated chart validates.

    reports_to: null

3.3  validate — check an org before running jobs

terminal
agent_factory validate --root orgs/Demo
✔ expected output
OK: orgs/Demo is a valid org (23 roles).
⚠️
If validation fails you get the specific reason (a bad reports_to link, an unknown tool id, a missing goal) with exit code 1 — fix the YAML and re-run. Always re-run validate after hand-editing org.yaml.

4Run work

📋
Purpose: enqueue a task for a specific role and watch it execute against the durable job ledger. Every job is stored — with results, events, and status — in orgs/<name>/.agentfactory/jobs.db.
terminal · run a job
agent_factory run --org orgs/Demo --role worker_research_1 ^
    --task "List the quarterly targets." --approval deny
✔ expected output (fake provider)
job #1 [worker_research_1] -> done in 1 step(s)
events:
--- output ---
List the quarterly targets.

Notes. --role must be a role id from orgs/Demo/roles/ (e.g. lead_exec, director_marketing, worker_research_1). --max-steps caps the agent loop; use --provider/--model to override the role's configured LLM for one run (see §8).

4.1  Approval modes — the main safety dial

When an agent wants to call a tool, its risk tier and the org's approval policy decide what happens. --approval is your per-run override:

Flag valueBehaviorUse when
askPause and prompt you in the terminal for each gated tool callInteractive runs where you want control
denyRefuse all gated calls automatically (job may end blocked)Unattended runs, CI, first dry-run of a new role
allowAuto-approve all gated callsTrusted, low-risk setups
🛡️
What "gated" means. A tool call is gated when the tool's risk tier is high, or the tool writes outside the org and the org's risk tier is review_external. Grants in org.yaml / role YAML decide which tools each role may use at all; the approval policy decides when using them needs a human.

4.2  jobs — the durable ledger

terminal
agent_factory jobs --org orgs/Demo
✔ expected output
id   org            role                     status    task
1    Demo Co        worker_research_1        done      List the quarterly targets.

Statuses: queued → running → done, or error / blocked (e.g. all tool calls needed approval). Every job's events and final output are stored in .agentfactory/jobs.db (see §10).

5Memory & proactivity

📋
Purpose: capture knowledge the whole org shares (context) and let leads propose and execute their own next steps within guardrails (ambition).

5.1  context — the shared company memory

Capture facts the whole workforce should be able to query — the "diary flow". Agents see relevant context in their prompts, and roles granted the memory tool can read/search it themselves.

terminal · add, list, search
# add an entry:  context --org <org> --add <key> --detail <text>
agent_factory context --org orgs/Demo --add diary/today ^
    --detail "Client wants a demo before signing."

# list everything
agent_factory context --org orgs/Demo

# search by substring
agent_factory context --org orgs/Demo --search demo
✔ expected output of  list / search (same table)
key                                  source     content
diary/today                          diary      Client wants a demo before signing.
💡
Notes. source records where the entry came from (diary = you typed it; ambition = the proactive loop logged a proposal/execution). Adding the same --add key again updates the entry.

5.2  ambition — the proactive "do smart things" loop

Let a high-proactivity lead initiate net-new work against the north star, quarterly goals, and captured context: it proposes actions (risk-rated, prioritized), then executes up to --max-actions of them as real jobs.

💡 Proposerisk-rated, prioritized next steps from goals + context
→
🧮 Evaluate--max-risk ceiling, tool grants, approval gate
→
✅ Executeup to --max-actions become real jobs in the ledger
terminal
agent_factory ambition --org orgs/Demo --role lead_exec --max-actions 2
✔ expected output (fake provider — real models produce concrete titles)
Proposals from lead_exec (proactivity 5):
  - <short title> (risk=medium, priority=1)
      action: <concrete task a worker should do>

Executed 1 action(s):
  job #2 [<short title>] -> done
⚠️
Guardrails. Only roles with proactivity_level >= 3 initiate (the bootstrap lead has level 5). A proposal whose risk exceeds the --max-risk ceiling is proposed but not executed, and requires_approval tools still go through the approval gate. Executed proposals become real jobs (and context entries), so status and brief see them.

6Observability

📋
Purpose: answer "what is my workforce doing right now?" and "what should I do today?" without reading the database.

6.1  status — mission control

terminal
agent_factory status --org orgs/Demo
✔ expected output
Mission control — Demo Co
  Jobs: 2 total  (queued=0, running=0, done=2, error=0, blocked=0)
  Open insights: 1
  Pending channel messages: 0

  Recent jobs:
    #2 [director_marketing] done: <concrete task a worker should do>
    #1 [worker_research_1] done: List the quarterly targets.

  Open insights: none

  Recent approval events: none

--limit controls how many recent jobs are shown (default 20).

6.2  observe — the observer/watchdog pass

Runs the cheap observer role to surface friction, access gaps, blockers, contradictions, and opportunities as insights in the store — not a dashboard, input for the brief.

terminal
agent_factory observe --org orgs/Demo --limit 3
✔ expected output (fake provider)
Observer observer surfaced 1 finding(s):
  [info/friction] <short title>
      detail: <what you found>
      suggest: <what to do about it>

Each finding is [level/kind] — e.g. info/friction warn/access_gap blocker. --role lets you use a different observer role; the default is the org's observer role (or the lead).

6.3  brief — "what should I do today"

Turns open insights + context + job state into a short, prioritized action plan (WHAT / WHO / FIRST STEP) as if the org lead were briefing the founder.

terminal
agent_factory brief --org orgs/Demo
✔ output: the brief prompt sent to the lead's model (fake provider echoes it verbatim)
You are Org Lead (Chief of Staff) (role `lead_exec`) acting as the founder's morning brief for the workforce "Demo Co".

STATE OF THE WORKFORCE
Job counts: 2 total (queued=0, running=0, done=2, error=0, blocked=0). Open insights: 1. Recent jobs: #2 [director_marketing] done: ... #1 [worker_research_1] done: ...

OPEN INSIGHTS
- [info/friction] <short title>. (<what you found>) Suggestion: <what to do about it>

CAPTURED CONTEXT
[diary/today] (diary) Client wants a demo before signing. ...

Produce a short, prioritized "what should I do today" plan ...
🪞
Fake provider and placeholders. fake is an echo client, so outputs contain placeholders like <short title>. With openai/ollama you get real content in the same shape — the commands are identical, only the text inside changes.

7Talk to your workforce M6

📋
Purpose: the shared channel is how a human teammate asks the workforce things: you post into #general, a channel worker runs the addressed role through the normal agent loop, and the agent's answer is posted back into the same channel as a reply.
👤 Youchannel post --text "…" --role lead_exec
→
💾 #general (SQLite)message queued as pending
→
⚙️ channel workerclaims pending → runs the role (tools, approvals, ledger)
→
💬 Replyagent's answer posted back to the channel

7.1  channel post — a human asks something

terminal
agent_factory channel post --org orgs/Demo ^
    --text "Did the client respond to my email?" --role lead_exec
✔ expected output
posted message #1 to #general (addressed to lead_exec) — queued for an agent reply

--role addresses a specific role (default: the org lead); omit it to let the lead route the question. --author overrides the displayed human name (default: the org founder).

7.2  channel worker — agents answer in-channel

terminal
agent_factory channel worker --org orgs/Demo
✔ expected output (fake provider)
#general: answered 1 message(s)
  #1 by 1 step(s): A human teammate posted this into the shared channel #general:

Did the client r...

Notes. The worker claims pending messages atomically (pending → running → done in SQLite), so a second worker or a restart never double-answers. --max-messages (default 5) bounds one worker run; --approval, --provider, --model, --temperature behave exactly like run; --role forces one role to answer regardless of addressing. The answering role runs with its normal grants, so tools it uses are recorded in the job ledger like any other job.

7.3  channel list — read the conversation

terminal
agent_factory channel list --org orgs/Demo
✔ expected output (newest first; * = human, -> = agent reply)
#general (2 message(s), newest first)
-> #2   [lead_exec:Org Lead (Chief of Staff) (lead_exec)] (done) A human teammate posted this into the shared channel #general:

Did th...
*  #1   [human:Founder] -> lead_exec (done) Did the client respond to my email?

Both messages show (done) — a question stays pending until a worker claims it, then running while answered, then done once the reply is posted. --channel switches channels (default general).

8Providers & models

📋
Purpose: choose where the intelligence comes from and override it per-run when needed.

Every command that runs an LLM (run, ambition, observe, brief, channel worker) accepts the same two overrides:

FlagMeaningExample
--provideropenai | ollama | fake for this one run--provider ollama
--modeloverride the role/environment model; may carry a provider/ prefix--model ollama/qwen2.5:7b

Rules

  • Defaults come from AGENT_FACTORY_PROVIDER (default openai) and the role's model tier (fast / smart / big, driven by the org's budget_tier).
  • If --model has a provider prefix that conflicts with --provider (e.g. --provider openai --model ollama/qwen2.5:7b), you get a clear configuration error instead of a silent mismatch.
  • Per-role environment models: set MODEL_DEFAULT, MODEL_FAST, MODEL_SMART, MODEL_BIG, or role-specific MODEL_<ROLE_ID> vars — probe shows every pair it finds.

Available providers

ProviderNeedsGood for
fakenothingtests, demos, headless smoke runs (echoes input)
openaiOPENAI_API_KEY (+ optional OPENAI_BASE_URL), pip install -e ".[openai]"production-quality work
ollamalocal Ollama at http://localhost:11434/v1 (override OLLAMA_BASE_URL/OLLAMA_MODEL), pip install -e ".[ollama]"private/local models (Gemma, Qwen, …)
⚠️
Anthropic is not wired yet. Installing the optional Anthropic package does not enable an Anthropic provider.

Live and stubbed tools

The currently live tools are files, web, memory, and channel. Third-party tool ids such as notion, gmail, calendar, slack, stripe, supabase, github, sheets, docs, crm, cms, payments, and analytics are declared integration stubs. Calling one returns a STUB message and does not modify the external service.

11Troubleshooting & FAQ

🔧 run says the role does not exist.
Role ids are file names under roles/ without .yaml — check orgs/Demo/roles/ or org.yaml.
🔧 A job ends blocked.
Every tool the agent tried required approval and --approval deny refused them all. Re-run with --approval ask to approve interactively, or lower the tool risk in the role's YAML.
🔧 bootstrap fails validation.
Read the specific error (bad reports_to link, unknown tool, missing goal). If hand-editing org.yaml, re-run validate before running jobs.
🔧 The output contains <short title> placeholders.
You are on the fake provider — it echoes prompts for deterministic offline runs. Switch to openai/ollama for real content.
🔧 probe reports [FAIL] ...
Check OPENAI_API_KEY / base URL (OpenAI) or that Ollama is running (ollama serve) and the model is pulled (ollama pull qwen2.5:7b).
🔧 A third-party tool returns STUB.
This is expected for the integrations listed in the live/stubbed tools section. Use files, web, memory, or channel for the implemented tool surface, or register a local MCP-style server through the runtime API.
❓ Two channel workers at once?
Safe. Message claims are atomic (pending → running), so each question is answered exactly once.
❓ Can I extend the tools?
Yes — see docs/ARCHITECTURE.md: the Tool catalog (runtime/tools.py) and register_tool_server() for MCP-style local servers (runtime/toolservers.py) are the extension points; new tools inherit the same grant + risk + approval gating.
